# Feature: Knowledge tab backend - assistant-scoped knowledge

**From build-plan:** feature 23d

**Status:** complete

## Goal

Add `assistant_id` scoping to `KnowledgeSource` and `Chunk`, and make retrieval actually filter by
it - closing the gap `apps/api/app/services/retrieval.py`'s own docstring has documented since
item 19: "assistant_id is validated... but is not yet a further narrowing filter... no feature yet
assigns a knowledge source to one specific assistant." Every knowledge source created from now on
must belong to exactly one assistant; retrieval only ever returns that assistant's own chunks,
matching CLAUDE.md section 11's stated architecture ("pgvector(1536), scoped by org + workspace +
assistant... Retrieval filters by organization, workspace, and assistant - always"). Backend only
- 23e builds the Knowledge tab UI that actually creates and manages sources through this.

## Design reference

None. Backend-only.

## Architecture decisions (read before building)

- **`assistant_id` is a nullable column at the database level, but required going forward at the
  API layer.** The dev database already has 2 real `KnowledgeSource` rows created before this
  feature existed (checked directly, not assumed), with no assistant to sensibly assign them to.
  A `NOT NULL` migration would either need a fabricated default (wrong) or force-deleting real
  rows (unnecessary and destructive for no benefit). Instead: the column is nullable at the
  schema level so those two orphaned rows simply become "unassigned, excluded from every
  assistant's retrieval" - a correct, harmless outcome - while every *new* knowledge source is
  required to specify a real `assistant_id` via the request schema (Pydantic `Field(...)`, no
  default), so nothing created from this point forward can end up unassigned by accident.
- **`Chunk.assistant_id` is denormalized from its parent `KnowledgeSource`, mirroring
  `organization_id`/`workspace_id`'s own exact precedent** (`app/models/chunk.py`'s own docstring:
  "denormalized here... because retrieval filters directly on them on the hot in-call path"). Set
  once, at chunk-write time, by reading `knowledge_source.assistant_id` - never a second parameter
  threaded independently through the chunking pipeline, so it can never drift from its parent
  source's own assignment.
- **The three creation paths (file upload, website crawl, manual FAQ) each gain a required
  `assistant_id`, validated with `assistant_service.get_assistant`** - the same "does this
  resource actually belong to this workspace" check `AssistantVersion`'s prompt-template
  reference already uses, raising `AssistantNotFound` (a new 404) exactly like every other
  cross-tenant guard in this codebase.
- **The file-upload route needs `assistant_id` as a form field, not JSON** - `upload_knowledge_source`
  is a `multipart/form-data` endpoint (`UploadFile`), so `assistant_id` arrives via FastAPI's
  `Form(...)`, not a Pydantic body schema; the other two (website, manual FAQ) already use JSON
  payload schemas and gain a plain required field.
- **`search_by_similarity` gains a required `assistant_id` parameter and filters on it directly**
  - replacing the "validated but not yet narrowing" behavior `retrieval.py`'s docstring has
  described since item 19. `retrieve()`'s own docstring is updated to stop describing this as a
  known gap, since after this feature it no longer is one.
- **Two build steps.** Step 1 makes knowledge sources assistant-owned (model, migration, creation
  paths, existing tests updated) without yet touching retrieval - a complete, independently
  correct state ("every new knowledge source belongs to an assistant") that doesn't yet change
  retrieval behavior. Step 2 threads `assistant_id` through chunk writes and the retrieval query
  itself, closing the actual gap, proven by a new cross-assistant isolation test - the real payoff,
  kept separate so each step's diff stays reviewable.

## In scope

- **`apps/api/app/models/knowledge_source.py`** - `assistant_id: uuid.UUID | None`, FK to
  `assistants.id` (`ondelete="CASCADE"`), indexed.
- **`apps/api/app/models/chunk.py`** - `assistant_id: uuid.UUID | None`, FK to `assistants.id`
  (`ondelete="CASCADE"`), indexed, mirroring `organization_id`/`workspace_id`'s exact shape.
- **A new Alembic migration** adding both nullable columns (autogenerated, reviewed - no backfill,
  no `server_default`; the 2 existing rows stay `NULL`).
- **`apps/api/app/schemas/knowledge_source.py`** - `WebsiteKnowledgeSourceCreate`/
  `ManualFaqKnowledgeSourceCreate` gain a required `assistant_id: uuid.UUID`;
  `KnowledgeSourceResponse` gains `assistant_id: uuid.UUID | None`.
- **`apps/api/app/services/knowledge_source.py`** - `upload_knowledge_source`,
  `create_website_knowledge_source`, `create_manual_faq_knowledge_source` each gain a required
  `assistant_id: uuid.UUID` parameter, validated via `assistant_service.get_assistant` before
  creating the `KnowledgeSource` row; `_parse_and_chunk_document`/`_crawl_and_reconcile` pass
  `assistant_id=knowledge_source.assistant_id` into `chunk_repo.replace_for_source`.
- **`apps/api/app/services/faq_entry.py`** - passes `assistant_id=knowledge_source.assistant_id`
  into `chunk_repo.upsert_for_faq_entry` (the knowledge source is already loaded at that call
  site).
- **`apps/api/app/repositories/knowledge_source.py`** - `KnowledgeSource(...)` construction sites
  gain `assistant_id`.
- **`apps/api/app/repositories/chunk.py`** - `replace_for_source`/`upsert_for_faq_entry` gain an
  `assistant_id: uuid.UUID | None` parameter, threaded into `Chunk(...)`; `search_by_similarity`
  gains a required `assistant_id: uuid.UUID` parameter and an added `Chunk.assistant_id ==
  assistant_id` filter.
- **`apps/api/app/services/retrieval.py`** - `retrieve()` passes `assistant_id` through to
  `search_by_similarity`; docstring updated to reflect the gap is now closed;
  `_assert_assistant_in_workspace` stays (still needed to reject a cross-workspace assistant_id).
- **`apps/api/app/api/v1/knowledge_sources.py`** - the three creation routes accept and forward
  `assistant_id` (`Form(...)` for upload, payload field for the other two); catch
  `AssistantNotFound` alongside the existing `WorkspaceNotFound` handling.
- **Existing tests updated**: `test_knowledge_sources.py`, `test_website_knowledge_sources.py`,
  `test_faq_entries.py`, `test_document_chunking.py` (every knowledge-source creation call gains a
  real `assistant_id`); `test_retrieval.py`/`test_internal_retrieval.py`/`test_context_builder.py`
  updated as needed for the new required parameter.
- **New tests**: a route-level 404 test for an `assistant_id` from a sibling workspace (mirroring
  every other cross-tenant test in this codebase); a retrieval-level test proving two assistants
  in the same workspace, each with their own knowledge source, never see each other's chunks.

## Out of scope

- **The Knowledge tab UI itself** - 23e.
- **Backfilling or deleting the 2 existing unassigned rows.** They stay exactly as they are,
  simply excluded from retrieval going forward - not this feature's job to clean up.
- **Allowing a knowledge source to be shared across multiple assistants.** One knowledge source,
  one assistant - matches what was actually asked for; a many-to-many model is a bigger, different
  design not implied by "embed knowledge inside the assistant editor."
- **Any change to `Assistant` deletion behavior.** Assistants are archived, never deleted, in this
  codebase today - the `ondelete="CASCADE"` FK is future-proofing for if that ever changes, not a
  new capability this feature adds.
